OOP Question Bank & Interviewer Guide

Twenty calibrated questions for screening mid-to-senior full-stack data scientists, each with a reference solution, the skills it probes, scoring anchors, and follow-ups — built to train interviewers and standardize how we grade candidates.

20 questions 1-hour session = 3–4 questions ≤15 min each 0–4 scoring rubric Tiers: F / M / A

How to run a session

Pick 3–4 questions spanning tiers (≥1 Foundational warm-up, ≥1 Advanced). Let the candidate think aloud; score each on the 0–4 rubric, capturing signal, not just correctness.

Scoring rubric (per question)

  • 0
    No signal. Can't start; fundamental misconceptions.
  • 1
    Emerging. Partial recall, heavy hints, code doesn't run.
  • 2
    Competent. Correct core with minor gaps; runs after small fixes.
  • 3
    Strong. Correct, idiomatic, explains why, handles edge cases.
  • 4
    Exceptional. Adds trade-offs, alternatives, a performance/maintenance lens.

Calibration principles (read before grading)

  • Reward the library instinct. A senior who says “I'd use NumPy/pandas/sklearn/dataclasses here” and explains when hand-rolling is justified should score higher, not be dinged for “not implementing it.”
  • Credit the mental model, not the term. For recitation-prone topics (MRO, NotImplemented, descriptors) grade the reasoning, not the vocabulary.
  • Senior bar: clears Advanced questions with little prompting and volunteers trade-offs.
  • Fairness: descriptors (Q15) and low-level mechanics may under-credit strong applied DS who never needed them — use as discriminators, not gates.
  • Time: budgets are split as code ~X / discuss ~Y. If a candidate stalls on syntax, move to discussion — we're screening design judgment.

Q01

The shared mutable class attribute

FoundationalState & attributes≤8 min · code ~3 / discuss ~5

Prompt

A teammate reports that two Dataset objects share data: adding a sample to one shows up in the other. Explain the bug, fix it, and explain class vs. instance attributes.

class Dataset:
    samples = []
    def __init__(self, name):
        self.name = name
    def add(self, x):
        self.samples.append(x)

Reference solution

class Dataset:
    def __init__(self, name):
        self.name = name
        self.samples = []          # per-instance state
    def add(self, x):
        self.samples.append(x)

Skills tested

Attribute lookup order, mutation vs. rebinding — the single most common Python OOP bug, and the root cause of subtle data-leakage bugs in stateful estimators.

Why each point matters

  • samples lives on the class, so all instances share one list object.
  • self.samples.append(x) reads samples (found on the class, since no instance attribute shadows it) and mutates it in place — it never rebinds, so every instance sees the change.
  • Assigning self.samples = [] in __init__ creates a distinct instance attribute that shadows the class one.
  • Class attributes are right for constants/shared config (DEFAULT_BATCH = 32); mutable class attributes are a footgun.

Scoring anchors

2
Moves samples into __init__ but can't explain why.
3
Explains lookup order + mutate-vs-rebind clearly.
4
Connects it to the mutable-default-argument trap and to real DS bugs (a model class accumulating self.losses_/self.history shared across instances).
Reward / watch for: the candidate who immediately asks “is this a shared reference?” — that instinct prevents train/test-leakage-class bugs.

Follow-up

Show def add(self, x, bucket=[]) — same bug class (mutable default argument). Why does it persist across calls?

Q02

__repr__ vs __str__ on a model object

FoundationalData model≤8 min · code ~3 / discuss ~5

Prompt

Why does a list of model objects print as [<Model object at 0x7f…>, …] in a notebook? Implement __repr__ and __str__ for a (possibly fitted) LinearModel. What happens if you define only one?

Reference solution

class LinearModel:
    def __init__(self, n_features, lr=0.01):
        self.n_features = n_features
        self.lr = lr
        self.coef_ = None                       # set after fit

    def __repr__(self):                         # dev-facing, unambiguous
        return (f"LinearModel(n_features={self.n_features}, "
                f"lr={self.lr!r}, fitted={self.coef_ is not None})")

    def __str__(self):                          # human summary
        state = "fitted" if self.coef_ is not None else "unfitted"
        return f"Linear model on {self.n_features} features ({state})"

Skills tested

The two string protocols and developer ergonomics — a good __repr__ is the highest-leverage debugging aid in data work (notebooks, logs, tracebacks).

Why each point matters

  • __repr__: unambiguous, developer-facing, ideally round-trips. Used in the REPL, inside containers (a list prints each element's repr), and in logs/tracebacks — that's why notebooks show object addresses without it.
  • __str__: human-readable; used by print(), str(), and f-string {x}.
  • Define only __repr__ → __str__ falls back to it. Not the reverse — so always define __repr__ first.

Scoring anchors

2
Writes both but conflates their audiences.
3
Knows containers use repr, knows the fallback direction, uses !r.
4
Frames __repr__ as a debugging investment; notes “eval-able” is the ideal but “useful description” is the real rule.
Reward / watch for: surfacing fitted-state in __repr__ (like sklearn) — shows they've debugged real pipelines.

Follow-up

Should repr always be eval-able? (No — for many objects “a useful, unambiguous description” is the goal.)

Q03

@classmethod vs @staticmethod & alternative constructors

Foundational+Methods≤12 min · code ~6 / discuss ~6

Prompt

Explain instance vs @classmethod vs @staticmethod. Add an alternative constructor from_csv and a validation helper to a TimeSeries. Why return cls(...) instead of TimeSeries(...)?

Reference solution

class TimeSeries:
    def __init__(self, timestamps, values):
        self.timestamps = timestamps          # numeric epoch seconds
        self.values = values

    @classmethod
    def from_csv(cls, path):
        ts, vals = [], []
        with open(path) as f:
            for line in f:
                t, v = line.strip().split(",")
                ts.append(float(t)); vals.append(float(v))   # parse to numbers
        return cls(ts, vals)                  # respects subclasses

    @staticmethod
    def is_regular(timestamps, tol=1e-9):
        if len(timestamps) < 2:
            return True                       # vacuously regular
        deltas = [b - a for a, b in zip(timestamps, timestamps[1:])]
        return max(deltas) - min(deltas) <= tol

Skills tested

The factory pattern, the role of cls, inheritance-awareness, and numeric-edge-case discipline.

Why each point matters

  • Instance method takes self; classmethod takes cls (ideal for alternative constructors); staticmethod takes no implicit arg (a cohesive utility namespaced on the class).
  • Returning cls(...) means a subclass Daily(TimeSeries) gets Daily.from_csv() returning a Daily — not a TimeSeries.
  • Correctness: timestamps must be parsed to numbers, or is_regular's b - a raises TypeError. Guard length ≤ 1, and compare spacing with a tol because float gaps rarely match exactly.

Scoring anchors

2
Knows the three method types; reaches for @classmethod for from_csv.
3
Explains the cls subclass-correctness benefit; parses inputs correctly.
4
Raises the float-equality issue unprompted; notes real code would wrap pd.read_csv rather than hand-parse.
Reward / watch for: “in production this is pd.read_csv; the lesson is cls for subclass-safe factories.” Don't penalize skipping the hand-parse.

Follow-up

Could is_regular be a module function instead? (Yes — staticmethod is mostly about cohesion/discoverability.)

Q04

@property & cached_property for derived features

Foundational+Encapsulation≤12 min · code ~6 / discuss ~6

Prompt

Make fahrenheit a read-only computed property of celsius, and validate celsius ≥ absolute zero. Then: an expensive derived feature is recomputed on every access — fix it. When is a property worth it, and what does it cost?

Reference solution

from functools import cached_property

class Reading:
    def __init__(self, celsius, signal):
        self.celsius = celsius            # routes through the setter
        self.signal = signal

    @property
    def celsius(self):
        return self._celsius

    @celsius.setter
    def celsius(self, value):
        if value < -273.15:
            raise ValueError("below absolute zero")
        self._celsius = value

    @property
    def fahrenheit(self):                 # cheap, always fresh
        return self._celsius * 9 / 5 + 32

    @cached_property
    def spectral_features(self):          # expensive, computed once
        return expensive_fft(self.signal)

Skills tested

Encapsulation without breaking the API, computed attributes, and the lazy-vs-fresh trade-off behind cached_property.

Why each point matters

  • A property gives attribute syntax backed by method behavior (validation, derivation). You can convert a plain attribute into a property without changing callers — so start public, add logic only when needed (“uniform access”).
  • __init__ assigning self.celsius reuses the setter's validation — no duplication.
  • cached_property computes once and stores the result in the instance __dict__; great for expensive derived features. Caveat: the cache won't refresh if inputs change, and it needs a writable __dict__ (clashes with __slots__).

Scoring anchors

2
Writes the property + setter validation.
3
Reuses the setter in __init__; reaches for cached_property for the expensive case.
4
Names the staleness caveat and the __slots__ interaction; avoids premature getters/setters (“don't write Java in Python”).
Reward / watch for: recognizing that caching derived features introduces a staleness/invalidation problem.

Follow-up

Add a fahrenheit setter that updates celsius. How would you invalidate spectral_features when signal changes?

Q05

__eq__ / __hash__ for a cache / feature key

IntermediateData model≤12 min · code ~5 / discuss ~7

Prompt

You key a feature cache by (model_name, version, feature_hash). Implement a CacheKey value object usable as a dict key / set member. What happens to hashability once you define __eq__? State the contract — and what breaks if a key's fields mutate after insertion?

Reference solution

class CacheKey:
    def __init__(self, model_name, version, feature_hash):
        self.model_name = model_name
        self.version = version
        self.feature_hash = feature_hash

    def __eq__(self, other):
        if not isinstance(other, CacheKey):
            return NotImplemented
        return ((self.model_name, self.version, self.feature_hash)
                == (other.model_name, other.version, other.feature_hash))

    def __hash__(self):
        return hash((self.model_name, self.version, self.feature_hash))

# Idiomatic shortcut: @dataclass(frozen=True) generates all of this.

Skills tested

The hash/eq invariant, value semantics, how set/dict actually work, and NotImplemented.

Why each point matters

  • Defining __eq__ sets __hash__ = None → the class becomes unhashable (Python's safety default, since custom equality usually invalidates the identity hash). You must define __hash__ too.
  • Contract: a == b ⟹ hash(a) == hash(b) (the converse need not hold — collisions are fine). Hash from the same immutable fields used in __eq__.
  • Mutation trap: change a field after inserting into a set/dict and the object lands in the wrong hash bucket — lookups silently miss. Keys must be effectively immutable.
  • Return NotImplemented (not False) for foreign types so Python can try the reflected comparison.

Scoring anchors

2
Implements both, hashes a tuple of fields.
3
States the contract and the “define eq → unhashable” rule.
4
Explains the mutate-after-insert failure, returns NotImplemented, and reaches for @dataclass(frozen=True) as the real-world shortcut (also sets __hash__).
Reward / watch for: “I'd make this a frozen dataclass” — the idiomatic, less error-prone answer.

Follow-up

Why does @dataclass(eq=True, frozen=False) also make instances unhashable?

Q06

Dataclasses: frozen, field, and the hashability rule

IntermediateModern Python≤12 min · code ~6 / discuss ~6

Prompt

Rewrite a boilerplate class as a @dataclass for an immutable experiment config: make it frozen, give a field a mutable default safely, and exclude a timestamp from equality. Precisely: which defaults does @dataclass reject, and why is that not a complete safety net?

Reference solution

from dataclasses import dataclass, field

@dataclass(frozen=True)
class ExperimentConfig:
    name: str
    params: dict = field(default_factory=dict)          # safe per-instance
    created_at: float = field(default=0.0, compare=False)

Skills tested

Modern stdlib fluency, immutability/hashability, and a precise understanding of the mutable-default guard (a deeper version of Q1).

Why each point matters

  • @dataclass generates __init__, __repr__, __eq__ from annotated fields.
  • The precise rule: dataclasses reject a default whose type is unhashable (type(default).__hash__ is None) — so list/dict/set raise ValueError at class definition. It is a hashability heuristic, not a true mutability check: a mutable-but-hashable default (e.g., a normal custom object) is silently shared across instances. So default_factory is the real fix, not just a way to satisfy the linter.
  • frozen=True blocks attribute writes (FrozenInstanceError) and generates a __hash__ — so instances are hashable iff every compared field is itself hashable. A dict field like params still raises at hash() time (a common gotcha — use a hashable type or compare=False if you need it as a key). Immutability also prevents the “mutate a shared config → corrupt another experiment / leak across runs” bug.
  • compare=False excludes created_at, so two runs with identical config compare equal regardless of when they ran.

Scoring anchors

2
Uses frozen + default_factory + compare=False correctly.
3
Explains why bare = {} is the Q1 bug and that the dataclass raises on it.
4
States the unhashable-type heuristic precisely and that it's not a complete safety net; mentions slots=True, kw_only, __post_init__ for validation.
Reward / watch for: connecting frozen config to reproducibility / leakage safety, not just boilerplate reduction.

Follow-up

How would you validate name is non-empty in a frozen dataclass? (__post_init__ with object.__setattr__ for any normalization.)

Q07

Abstract base classes vs Protocol

IntermediateInterfaces & typing≤13 min · code ~6 / discuss ~7

Prompt

Define an Estimator interface (fit, predict) with abc; show that a subclass missing predict can't be instantiated. When prefer an ABC over duck typing, and how does typing.Protocol differ?

Reference solution

from abc import ABC, abstractmethod

class Estimator(ABC):
    @abstractmethod
    def fit(self, X, y): ...
    @abstractmethod
    def predict(self, X): ...

class MeanRegressor(Estimator):
    def fit(self, X, y):
        self.mu_ = sum(y) / len(y); return self
    def predict(self, X):
        return [self.mu_] * len(X)
# A subclass without predict -> TypeError at instantiation.

# Structural alternative:
from typing import Protocol, runtime_checkable
@runtime_checkable
class SupportsPredict(Protocol):
    def predict(self, X): ...

Skills tested

Interface design, fail-fast contracts, and nominal (ABC) vs structural (Protocol) typing.

Why each point matters

  • An ABC can't be instantiated; a concrete subclass leaving any @abstractmethod unimplemented also can't (TypeError at construction) — fails fast and loud.
  • ABC when you own the hierarchy, want shared/base logic, and want explicit isinstance contracts.
  • Protocol for structural typing (“if it has predict, it qualifies”) — perfect for typing third-party/duck-typed objects you don't control, no inheritance needed; checked statically (and at runtime if @runtime_checkable).

Scoring anchors

2
Writes the ABC, knows abstract methods block instantiation.
3
Articulates fail-fast value and gives a real use (sklearn-style estimators).
4
Frames nominal vs structural, picks Protocol for “accept anything with .predict,” notes np.mean would replace the toy sum/len in practice.
Reward / watch for: choosing Protocol to type a function that accepts any model with .predict — decoupling without inheritance.

Follow-up

Can an ABC method have a default implementation a subclass may override? (Yes.) When does that beat a Protocol?

Q08

Operator overloading: a mergeable aggregate (__add__/__radd__)

IntermediateData model≤14 min · code ~7 / discuss ~7

Prompt

Implement RunningStats — a partial aggregate (count, sum, sum-of-squares) you can merge with + across shards/batches, exposing mean and variance. Make sum([s1, s2, s3]) work. Use NotImplemented correctly.

Reference solution

class RunningStats:
    """Mergeable partial aggregate — the combiner pattern in MapReduce."""
    def __init__(self, n=0, total=0.0, sq=0.0):
        self.n, self.total, self.sq = n, total, sq

    @classmethod
    def from_values(cls, xs):
        return cls(len(xs), sum(xs), sum(x * x for x in xs))

    @property
    def mean(self):
        return self.total / self.n if self.n else float("nan")

    @property
    def variance(self):
        return self.sq / self.n - self.mean ** 2 if self.n else float("nan")

    def __add__(self, other):
        if not isinstance(other, RunningStats):
            return NotImplemented                 # let Python try other side
        return RunningStats(self.n + other.n,
                            self.total + other.total, self.sq + other.sq)

    def __radd__(self, other):
        if other == 0:                            # sum() starts from int 0
            return self
        return NotImplemented

    def __repr__(self):
        return f"RunningStats(n={self.n}, mean={self.mean:.3f})"

Skills tested

Reflected operators, the NotImplemented singleton, and modeling a real distributed-aggregation primitive (not hand-rolled array math).

Why each point matters

  • sum(parts) computes 0 + s1 + …; 0 + s1 calls int.__add__ first → returns NotImplemented → Python falls back to s1.__radd__(0). Hence __radd__.
  • Returning the singleton NotImplemented (not raising, not False) tells Python to try the reflected operator; raising TypeError would short-circuit that.
  • Operator overloading is justified here because + has clear domain meaning (merge aggregates) — this is the combiner that lets you parallelize a mean/variance over partitions. (For elementwise array math you'd use NumPy, not a custom class.)

Scoring anchors

2
Implements __add__; forgets __radd__ so sum() raises.
3
Adds __radd__, explains the reflected-operator fallback and NotImplemented vs NotImplementedError.
4
Notes this is the map-reduce combiner pattern; mentions numerical stability (Welford / Kahan) for streaming variance.
Reward / watch for: recognizing the combiner pattern (mergeable, associative) and that elementwise vector math belongs in NumPy.

Follow-up

Difference between NotImplemented and NotImplementedError? Why is naive sum-of-squares variance numerically risky?

Q09

Context managers two ways

IntermediateResource mgmt≤12 min · code ~6 / discuss ~6

Prompt

Write a Timer context manager two ways — a class (__enter__/__exit__) and contextlib.contextmanager — that both expose .elapsed. How does __exit__ see exceptions, and when does returning True matter?

Reference solution

import time
from contextlib import contextmanager
from types import SimpleNamespace

class Timer:
    def __enter__(self):
        self.start = time.perf_counter()
        return self                       # bound to `as t`
    def __exit__(self, exc_type, exc, tb):
        self.elapsed = time.perf_counter() - self.start
        return False                      # do NOT suppress exceptions

@contextmanager
def timer():
    h = SimpleNamespace(elapsed=None)
    start = time.perf_counter()
    try:
        yield h                           # `as h`; h.elapsed filled on exit
    finally:
        h.elapsed = time.perf_counter() - start

Skills tested

The context-manager protocol, deterministic cleanup, exception flow, and contextlib.

Why each point matters

  • __enter__'s return value binds to the as target. __exit__ always runs — normal exit or exception.
  • On exception, __exit__ receives (exc_type, exc, tb); returning a truthy value suppresses it. Returning False/None lets it propagate (the safe default — accidental swallowing hides bugs).
  • In the generator form, try/finally around yield guarantees cleanup; code before yield is setup, after is teardown.

Scoring anchors

2
One correct implementation.
3
Both forms; knows the as-binding and that __exit__ always runs.
4
Explains exception suppression precisely, warns against accidental swallowing, cites real uses (DB sessions, temp files, torch.no_grad()-style scopes), mentions ExitStack.
Reward / watch for: unprompted caution about returning truthy from __exit__ and hiding exceptions.

Follow-up

How would you manage many resources opened in a loop? (contextlib.ExitStack.)

Q10

Iterables vs iterators (re-iterability)

IntermediateIteration≤13 min · code ~6 / discuss ~7

Prompt

Build a BatchLoader that yields fixed-size batches and can be iterated multiple times. What's the difference between an iterable and an iterator? Why can a class whose __iter__ returns self be looped only once?

Reference solution

class BatchLoader:
    def __init__(self, data, batch_size):
        self.data = data
        self.batch_size = batch_size
    def __iter__(self):                          # generator -> fresh each call
        for i in range(0, len(self.data), self.batch_size):
            yield self.data[i:i + self.batch_size]

Skills tested

The iteration protocol, generators, and statefulness — directly relevant to data pipelines / DataLoaders.

Why each point matters

  • Iterable: implements __iter__, returning a fresh iterator. Iterator: implements __next__ (and __iter__ returning self); it's stateful and single-use (raises StopIteration when done).
  • Writing __iter__ as a generator yields a brand-new iterator on every for loop → re-iterable.
  • If the object is its own iterator (__iter__ returns self with a cursor in __next__), the cursor is shared/exhausted, so a second loop yields nothing.

Scoring anchors

2
Produces batches but can't articulate iterable vs iterator.
3
Explains the distinction and why the generator form is re-iterable.
4
Connects to lazy/streaming memory efficiency (data that doesn't fit in RAM) and the single-pass gotcha that bites DataLoader/generator users.
Reward / watch for: mentioning generators give lazy, O(1)-memory streaming for large datasets.

Follow-up

Write the explicit __iter__/__next__ version and show it exhausts after one pass.

Q11

super(), MRO & cooperative mixins

AdvancedInheritance & MRO≤14 min · code ~4 / discuss ~10

Prompt

(a) Why must each mixin call super().setup()? (b) Predict the output and Model.__mro__. (c) What changes if Logged.setup omits its super() call?

class Base:
    def setup(self): print("Base")
class Logged(Base):
    def setup(self): print("Logged"); super().setup()
class Cached(Base):
    def setup(self): print("Cached"); super().setup()
class Model(Logged, Cached):
    def setup(self): print("Model"); super().setup()

Model().setup()

Reference solution

Model
Logged
Cached
Base
# Model.__mro__ == [Model, Logged, Cached, Base, object]

Skills tested

C3 linearization, cooperative super(), and the real mental model of method dispatch in mixin-heavy frameworks (Keras layers, DRF views, dataset base classes).

Why each point matters

  • (a) super() dispatches to the next class in the instance's MRO, not the literal parent. Each mixin must call super() or the chain stops and later mixins/base are skipped.
  • (b) MRO is computed by C3 linearization: local precedence (Logged before Cached because Model(Logged, Cached)) + monotonicity. Inside Logged, super().setup() goes to Cached — not Base. Base runs once because each class appears once in the MRO.
  • (c) If Logged drops its super() call, Cached and Base are skipped — the classic broken-cooperative-inheritance bug.

Scoring anchors

2
Gets the output but thinks super == parent.
3
Correct output + states “super follows the instance's MRO,” explains the single Base call.
4
States the C3 rules, predicts the (c) breakage, and ties it to real framework mixins they've used.
Reward / watch for: the mental model “super walks the MRO,” not memorizing the term “C3.”

Follow-up

What if a mixin's setup took different arguments than another's? (Cooperative methods must share a compatible signature — often *args, **kwargs.)

Q12

__slots__ and memory at scale

AdvancedPerformance≤12 min · code ~4 / discuss ~8

Prompt

You instantiate tens of millions of small objects and hit memory limits. Explain __slots__, rewrite a class to use it, and list the trade-offs. Then: is this even the right tool?

Reference solution

class Particle:
    __slots__ = ("x", "y", "mass")
    def __init__(self, x, y, mass):
        self.x, self.y, self.mass = x, y, mass

Skills tested

CPython's object model, memory/perf awareness at data scale, and knowing the costs — and the better alternative.

Why each point matters

  • By default each instance carries a __dict__ for dynamic attributes — flexible but heavy. __slots__ stores attributes in a fixed, array-like layout: less memory per instance and often slightly faster attribute access.
  • Trade-offs: (1) no new attributes beyond the declared slots; (2) no __dict__/__weakref__ unless added; (3) inheritance caveats — subclasses regain a __dict__ unless they also declare __slots__, and two slotted bases with non-empty slots raise a layout conflict; (4) clashes with cached_property/class-level defaults for slotted names.

Scoring anchors

2
Knows __slots__ saves memory; can write it.
3
Lists the main trade-offs (no dynamic attrs, inheritance caveats).
4
Says “profile first,” quantifies the win, and — crucially — notes the real fix for millions of records is columnar/NumPy/pandas/array, not millions of Python objects.
Reward / watch for: reaching for vectorized/columnar storage instead of micro-optimizing per-object overhead. That's the senior DS answer.

Follow-up

When is __slots__ the wrong tool? (When you should be using NumPy/pandas/Arrow.) How does @dataclass(slots=True) help?

Q13

Composition over inheritance

AdvancedDesign≤15 min · code ~5 / discuss ~10

Prompt

A DataPipeline needs optional, combinable behaviors: logging, caching, validation. Sketch why a class-per-combination inheritance design fails, then refactor to composition. When are mixins still appropriate?

Reference solution (sketch)

class Pipeline:
    def __init__(self, steps, *, logger=None, cache=None, validator=None):
        self.steps = steps
        self.logger = logger or NullLogger()       # null-object defaults
        self.cache = cache or NullCache()
        self.validator = validator

    def run(self, data):
        if self.validator:
            self.validator.check(data)
        key = self.cache.key(data)
        if (hit := self.cache.get(key)) is not None:
            self.logger.info("cache hit"); return hit
        for step in self.steps:
            data = step(data)
        self.cache.set(key, data)
        self.logger.info("computed")
        return data

Skills tested

Design judgment (SOLID), dependency injection, and recognizing combinatorial inheritance explosion. Open question — grade the reasoning.

Why each point matters

  • Inheritance for behavior combos explodes: LoggingPipeline, CachingPipeline, LoggingCachingValidatingPipeline, … — N behaviors → 2ᴺ classes.
  • Composition injects collaborators (strategy objects): behaviors are independent, swappable, and testable in isolation (pass a fake logger/cache). Null-object defaults keep run() branch-free.
  • Mixins remain fine for orthogonal, cross-cutting behavior designed to cooperate via super() (e.g., a SerializableMixin) — avoid deep stacks and shared mutable state.

Scoring anchors

2
Prefers composition but reasoning is vague.
3
Names the 2ᴺ explosion and injects collaborators; mentions testability.
4
Invokes open/closed + DI, shows swap (Redis vs in-memory cache), and resists over-engineering for the simple case.
Reward / watch for: talking about testing each behavior in isolation and swapping implementations behind an interface.

Follow-up

How would you unit-test caching behavior without a real cache? How does this enable swapping a backend?

Q14

Custom exception hierarchy

IntermediateError handling≤11 min · code ~5 / discuss ~6

Prompt

Design exceptions for a data-validation library: a base plus SchemaError and MissingValueError. Why a common base? Show catching at different granularities and chaining context with raise … from.

Reference solution

class DataError(Exception):
    """Base for all data-validation errors."""

class SchemaError(DataError):
    pass

class MissingValueError(DataError):
    def __init__(self, column):
        super().__init__(f"missing values in column {column!r}")
        self.column = column                       # structured payload

# usage
try:
    validate(df)
except MissingValueError as e:                     # specific
    fill_defaults(e.column)
except DataError:                                  # catch-all for this lib
    abort()

# chaining
try:
    int(raw)
except ValueError as e:
    raise SchemaError("expected integer id") from e

Why each point matters

  • A common base lets callers catch every library error with one except DataError while still handling subclasses finely — and keeps your errors distinct from built-ins.
  • Subclasses can carry structured data (e.column) for programmatic handling, not just a message string.
  • raise New(...) from original sets __cause__ and preserves the chain in the traceback; from None deliberately suppresses a noisy cause.

Q15

Descriptors for reusable hyperparameter validation

AdvancedData model≤15 min · code ~7 / discuss ~8

Prompt

Many estimators need validated hyperparameters (a probability in [0,1], a positive int). Write reusable descriptors instead of repeating property boilerplate. Explain __set_name__, __get__, __set__, and how @property relates.

Reference solution

class Probability:
    def __set_name__(self, owner, name):
        self._name = f"_{name}"                  # auto-captures attr name
    def __get__(self, obj, objtype=None):
        if obj is None:
            return self                          # class access -> descriptor
        return getattr(obj, self._name)
    def __set__(self, obj, value):
        if not 0.0 <= value <= 1.0:
            raise ValueError(f"{self._name[1:]} must be in [0,1]")
        setattr(obj, self._name, value)          # stored on the instance

class Classifier:
    threshold = Probability()
    def __init__(self, threshold):
        self.threshold = threshold              # triggers __set__

Skills tested

The descriptor protocol — the machinery behind properties/methods — and building reusable, DRY abstractions. Strong senior signal.

Why each point matters

  • A descriptor is any object defining __get__/__set__/__delete__; as a class attribute it intercepts instance attribute access.
  • __set_name__(owner, name) is called at class creation with the attribute name, so one descriptor knows where to store per-instance data (_threshold) — no manual wiring.
  • State lives on the instance (setattr(obj, self._name, …)), because one descriptor object is shared by all instances of the class — storing on the descriptor would leak state across instances.
  • @property is itself a descriptor; descriptors generalize it so one validator serves many attributes and classes — this is how sklearn/pydantic/attrs validate params under the hood.

Scoring anchors

2
Writes a working descriptor with hard-coded storage name.
3
Uses __set_name__, stores on the instance, explains why.
4
Explains data vs non-data descriptors (defining __set__ makes it a data descriptor that takes precedence over the instance __dict__) and that methods are descriptors too.
Reward / watch for: connecting descriptors to how pydantic/attrs/sklearn validation actually works.

Follow-up

Why store on the instance rather than on the descriptor? (Shared descriptor → per-instance state must live on the instance.) What's a data vs non-data descriptor?

Q16

A scikit-learn-style transformer (fit / transform / conventions)

Intermediate+DS-applied≤14 min · code ~7 / discuss ~7

Prompt

Implement a StandardScaler-like transformer with fit, transform, fit_transform. Store learned state, raise if transform runs before fit, and follow sklearn conventions. (Treat X as 1-D for brevity.) Then: why must you fit on train only?

Reference solution

class StandardScaler:
    def fit(self, X):
        n = len(X)
        self.mean_ = sum(X) / n
        var = sum((x - self.mean_) ** 2 for x in X) / n
        self.scale_ = var ** 0.5 or 1.0          # guard zero variance
        return self                               # enable chaining
    def transform(self, X):
        if not hasattr(self, "mean_"):
            raise RuntimeError("call fit() before transform()")
        return [(x - self.mean_) / self.scale_ for x in X]
    def fit_transform(self, X):
        return self.fit(X).transform(X)
# Real sklearn: per-column on 2-D arrays, np.mean(X, axis=0); raises NotFittedError.

Skills tested

Applying OOP to the core DS workflow; state management; library conventions; leakage awareness.

Why each point matters

  • Convention: learned attributes end with a trailing underscore (mean_, scale_) and are created in fit — signaling “fitted state.” Hyperparameters (constructor args) do not get the underscore.
  • fit returns self so you can chain and slot into pipelines.
  • Calling transform before fit must fail explicitly (sklearn raises NotFittedError).
  • Leakage: you fit on train only and transform both train and test — fitting on the full dataset leaks test statistics into training and inflates metrics.

Scoring anchors

2
Working fit/transform; stores state.
3
Trailing-underscore convention, return self, not-fitted guard.
4
Explains train/test leakage; notes per-column 2-D reality (axis=0) and where get_params/set_params/clone fit for grid search.
Reward / watch for: the leakage point volunteered unprompted — the clearest mid-vs-senior separator here.

Follow-up

To work in GridSearchCV, what contract must __init__ honor? (Params set, not validated/mutated, in __init__ only — so clone can deep-copy params, not learned state.)

Q17

Registry-based factory (Strategy) for model selection

Intermediate+Patterns≤13 min · code ~6 / discuss ~7

Prompt

Select among many model/strategy implementations by name at runtime (e.g., model: xgboost from a YAML config). Build a registry-based factory using a decorator to register classes. Why beat a long if/elif?

Reference solution

class ModelFactory:
    _registry = {}

    @classmethod
    def register(cls, name):
        def deco(model_cls):
            cls._registry[name] = model_cls
            return model_cls
        return deco

    @classmethod
    def create(cls, name, **kwargs):
        if name not in cls._registry:                  # narrow check first
            raise ValueError(f"unknown model {name!r}; "
                             f"have {list(cls._registry)}")
        return cls._registry[name](**kwargs)           # ctor errors propagate

@ModelFactory.register("linear")
class LinearModel:
    def __init__(self, lr=0.01): self.lr = lr

model = ModelFactory.create("linear", lr=0.1)

Skills tested

Strategy/Factory patterns, decorators as registration, the open/closed principle, and careful error handling.

Why each point matters

  • The decorator registers each class at import time, keyed by name; create looks up and instantiates.
  • Open/closed: add a model by writing a class + decorator — no edits to the factory or a central if/elif. New strategies can even live in plugins.
  • Correctness: check membership before constructing. Wrapping the constructor call in try/except KeyError would mis-report a KeyError raised inside the constructor as “unknown model” — a maddening bug.

Scoring anchors

2
Working registry + decorator.
3
Explains open/closed vs if/elif; clean error for unknown names.
4
Avoids masking constructor errors; flags pitfalls (module must be imported to self-register; name collisions); ties to config-driven ML.
Reward / watch for: noticing the error-masking trap, and that registration requires the plugin module to be imported.

Follow-up

How do you guarantee plugin modules self-register? (Explicit imports / entry points.)

Q18

Callable objects: __call__ vs closures

IntermediateData model≤12 min · code ~6 / discuss ~6

Prompt

Implement a parameterized, stateful callable — e.g., a FocalLoss(gamma) or a MovingAverage(window) whose instances are callable. Compare a class with __call__ to a closure. When prefer the class?

Reference solution

from collections import deque

class MovingAverage:
    def __init__(self, window):
        self.window = window
        self._buf = deque(maxlen=window)
    def __call__(self, x):
        self._buf.append(x)
        return sum(self._buf) / len(self._buf)
    def reset(self):
        self._buf.clear()

ma = MovingAverage(3); ma(10); ma(20); ma(30)   # -> 20.0

# Closure equivalent:
def moving_average(window):
    buf = deque(maxlen=window)
    def step(x):
        buf.append(x); return sum(buf) / len(buf)
    return step

Skills tested

__call__, stateful callables, and choosing between OO and functional styles.

Why each point matters

  • __call__ makes an instance behave like a function (ma(x)) while holding inspectable, resettable state — ideal for parameterized loss/metric objects you pass where a callable is expected (the Keras/PyTorch loss-as-object convention).
  • A closure is lighter but its state is hidden in a cell — harder to introspect, serialize, or extend.
  • Prefer the class when you need extra methods (reset), introspection, pickling/checkpointing, or subclassing; the closure for quick one-offs.

Scoring anchors

2
Implements one correctly.
3
Gives both; states both are “a function with memory.”
4
Picks class for testability/serialization (a stateful transform that must be checkpointed); notes closures aren't picklable by default; uses deque(maxlen=…) deliberately.
Reward / watch for: connecting __call__ to loss/metric/transform objects and pickling for checkpoints.

Follow-up

Why is deque(maxlen=…) better than a list here? How would you pickle the class vs the closure?

Q19

Shallow vs deep copy of a config/model

IntermediateCopy & state≤12 min · code ~5 / discuss ~7

Prompt

A teammate does cfg2 = copy.copy(cfg), mutates cfg2.params["lr"], and is surprised cfg.params["lr"] changed too. Explain shallow vs deep copy, fix it, show how to customize copying, and name a deepcopy performance trap.

Reference solution

import copy

class Config:
    def __init__(self, params, features):
        self.params = params          # dict
        self.features = features      # list

cfg = Config({"lr": 0.1}, ["age", "income"])
shallow = copy.copy(cfg)             # new Config, SAME inner dict/list
deep = copy.deepcopy(cfg)           # new Config, NEW inner dict/list
shallow.params["lr"] = 0.5           # also mutates cfg.params (shared ref!)
deep.params["lr"] = 0.9              # independent

class Model:
    def __init__(self, weights, conn=None):
        self.weights = weights
        self._conn = conn                       # un-copyable resource
    def __deepcopy__(self, memo):
        new = Model(copy.deepcopy(self.weights, memo))
        new._conn = self._conn                  # share, don't copy
        return new

Skills tested

Shallow vs deep copy, the shared-reference trap, __copy__/__deepcopy__, the memo dict, and copy-cost awareness.

Why each point matters

  • copy.copy (shallow): new top-level object, but copies references to nested objects → mutating nested state leaks between copies.
  • copy.deepcopy: recursively copies everything; the memo dict prevents infinite recursion on cycles and preserves shared identity within one copy.
  • Customize via __deepcopy__/__copy__ — e.g., don't deepcopy a DB connection / open file / huge shared array; share or re-open instead.
  • Perf trap: deepcopy of large arrays/DataFrames is slow and doubles memory; for big numeric state prefer explicit np copies or immutability.

Scoring anchors

2
Knows shallow vs deep verbally.
3
Fixes with deepcopy, explains the shared-reference leak.
4
Customizes __deepcopy__ for un-copyable resources, mentions memo/cycles and the deepcopy perf/memory cost.
Reward / watch for: “make the config an immutable frozen dataclass so copying isn't needed” — the design-level answer.

Follow-up

How does deepcopy relate to pickling? (Both rely on __reduce__/__getstate__ — see Q20.)

Q20

Serializing a stateful fitted object (pickle)

AdvancedSerialization≤14 min · code ~5 / discuss ~9

Prompt

You pickle a fitted transformer and load it in the serving environment; it fails to unpickle (or silently misbehaves). Walk through why pickling stateful objects is risky, what is/isn't picklable, and how to make a stateful estimator safely serializable. Where do __getstate__/__setstate__ and __new__ fit?

Reference solution

class FeatureEncoder:
    def __init__(self, db_url):
        self.db_url = db_url
        self._conn = connect(db_url)        # live, NOT picklable
        self.vocab_ = None                  # learned state, picklable

    def __getstate__(self):
        state = self.__dict__.copy()
        del state["_conn"]                  # drop the live connection
        return state

    def __setstate__(self, state):
        self.__dict__.update(state)
        self._conn = connect(self.db_url)   # rebuild on load

Skills tested

Persistence/reproducibility, __getstate__/__setstate__, the __new__-bypasses-__init__ subtlety, and the real-world hazards of model serialization.

Why each point matters

  • Pickle serializes the instance __dict__ by default; live resources (connections, file handles, threads/locks) and lambdas/closures/locally-defined classes aren't picklable → errors.
  • __getstate__ returns what to save (strip un-picklable handles); __setstate__ restores and rebuilds them. Pickle reconstructs the object via __new__ without calling __init__ — so don't rely on __init__ side-effects at load time.
  • Version skew: unpickling needs the same class importable at the same path; library drift (numpy/sklearn) can break or silently corrupt — pin versions, store metadata.
  • Security: never unpickle untrusted data — it can execute arbitrary code.

Scoring anchors

2
Knows pickle exists; names one unpicklable thing.
3
Uses __getstate__/__setstate__ to drop & rebuild a connection.
4
Covers __new__-bypasses-__init__, version skew, the security risk, and recommends joblib for numpy-heavy models / pinning / storing schema.
Reward / watch for: reproducibility instincts — pinning library versions, joblib over raw pickle for arrays, storing metadata alongside the artifact.

Follow-up

Why is unpickling untrusted data dangerous? How does joblib differ from pickle? Why might a model pickled in training silently give wrong predictions in serving?
